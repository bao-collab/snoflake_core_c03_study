## Streams (D3 Chunk 7)

Change-tracking object. Points at a table/view, records DML since last consumption — a **table delta**.

- Metadata columns: `METADATA$ACTION` (INSERT/DELETE), `METADATA$ISUPDATE`, `METADATA$ROW_ID`
- An UPDATE = DELETE + INSERT pair with `ISUPDATE = TRUE`
- **Offset advances only when consumed inside a DML transaction** (e.g. `INSERT INTO target SELECT * FROM my_stream`). A plain `SELECT` does NOT advance it.
- Types:
  - **standard** — all DML; tables & views
  - **append-only** — inserts only; cheaper; used for streaming ingestion
  - **insert-only** — external tables
- **Staleness**: goes stale if not consumed within the source table's data-retention period
- `SYSTEM$STREAM_HAS_DATA('my_stream')` → boolean check
- Multiple streams on one table are independent (each has its own offset)

### Table delta (concept)
The set of changes between two points in time, not full table contents. 10M-row table + 500 new rows → delta = those 500 rows.
- Why it matters: MERGE 500 rows instead of full-scanning 10M. Incremental processing.
- **A stream stores no copy of the rows** — only an **offset** (table version pointer). Snowflake computes the diff from that offset to the current version using **Time Travel metadata**.
- That's exactly why streams go stale: if the offset falls outside retention, the versions needed to compute the delta are gone.

## Tasks (D3 Chunk 8)

Scheduled/triggered SQL execution — single statement, stored proc, or script block.

- `SCHEDULE = 'n MINUTE'` or `USING CRON <expr> <timezone>`
- Compute: **serverless** (Snowflake-managed, per-second billing on actual usage) vs **user-managed warehouse** (`WAREHOUSE =`)
- Tasks are **created suspended** → must `ALTER TASK ... RESUME`
- Requires `EXECUTE TASK` privilege
- `WHEN SYSTEM$STREAM_HAS_DATA('my_stream')` — skips the run, **no compute charge**, when nothing is new

### Task graphs (DAGs)
DAG = Directed Acyclic Graph: one-way dependencies, no cycles. Children run after parents succeed.

```
        root_task            (only node with a SCHEDULE)
        /        \
  load_dims    load_facts    AFTER root_task
        \        /
        build_agg            AFTER load_dims, load_facts
```

Rules:
- **Exactly one root task** per graph — the only one with a `SCHEDULE`; all others use `AFTER <predecessor>`
- Child with multiple predecessors waits for **all** of them
- Children run only if the parent **succeeds**. Parent fails, or is skipped because its `WHEN` was false → branch below does not run
- Root won't start a new run while the previous graph run is still going (default; `ALLOW_OVERLAPPING_EXECUTION` overrides)
- **Resume children BEFORE the root**, or the root fires with dead branches. `SELECT SYSTEM$TASK_DEPENDENTS_ENABLE('root_task')` resumes the whole graph
- Limits: 1000 tasks/graph, 100 predecessors/task, 100 children/task
- Monitoring: `TASK_HISTORY()`, `COMPLETE_TASK_GRAPHS` / `CURRENT_TASK_GRAPHS` (Account Usage), Snowsight graph view

### Classic native ELT/CDC pattern
Snowpipe → landing table → Stream captures new rows → Task on schedule checks `STREAM_HAS_DATA` → MERGE into target.

## Unistore / Hybrid Tables (Domain 1)

**HTAP** = Hybrid Transactional/Analytical Processing — one system for OLTP (many small fast row reads/writes) and OLAP (large scans/aggregations). **Unistore** = the product name; **Hybrid Tables** = the actual object.

| | Standard table | Hybrid table |
|---|---|---|
| Storage | Columnar, immutable micro-partitions | Row store (+ columnar copy kept in sync) |
| Optimized for | Large scans, aggregation | Point lookups, single-row DML |
| Primary key | Not enforced (informational) | **Enforced, required** |
| Unique / foreign keys | Not enforced | **Enforced** |
| Indexes | No (pruning + search optimization) | **Secondary indexes** |
| Locking | Table-level on DML | **Row-level** |
| Latency | 100s ms – seconds | Single-digit to low tens of ms |
| Concurrency | Modest writes | High, many concurrent writers |

Key points:
- **PK is mandatory** and cannot be altered after creation — the most distinctive fact
- Constraints genuinely enforced (duplicate PK insert fails) — **the only place in Snowflake that's true**
- **Can join a hybrid table to a standard table in one query** — no pipeline, no copy. Core selling point.
- Same SQL surface, RBAC, governance (masking, row access policies), Time Travel
- Billed separately: own storage rate + "hybrid table requests" line item, on top of warehouse compute

Use cases: app-serving state (profiles, session, feature flags); transactional workflow/status tables; fast enrichment lookups during ingestion; small config/dimension tables an app writes and analytics joins immediately.

Limitations: no `COPY INTO`/Snowpipe into hybrid tables (use INSERT/MERGE or `INSERT INTO ... SELECT`); much lower size ceilings; no external tables, limited cloning/replication; not in every region/cloud.

**Exam:** on COF-C03 but lightly. Know: OLTP workload, row store, **enforced PK**, row-level locking, joinable with standard tables. Skip pricing and index syntax.

## NOT TESTED on COF-C03 — work knowledge only

### Openflow
Managed ingestion/integration service built on **Apache NiFi** (Datavolo acquisition). Sits *before* streams/tasks.
- Visual connector-based flows; NiFi processors + Snowflake connectors (SharePoint, Google Drive, Box, Slack, Kafka, Postgres/MySQL CDC, Workday…)
- First-class **unstructured data** handling (PDFs, docs) — the draw for RAG/Cortex pipelines
- Deployment: **Snowflake-deployed** (fully managed) or **BYOC** (your own VPC, data residency)
- Positioning: replaces Fivetran/Airbyte-style third-party ELT for many sources
- Already flagged in `snowflake-progress.md` as NOT TESTED until GA

### Managed dbt (dbt Projects on Snowflake)
Run dbt Core natively inside Snowflake — no separate orchestrator, no dbt Cloud, no container.
- Project lives as a workspace/Git-connected repo; you get a `DBT PROJECT` schema object
- `EXECUTE DBT PROJECT <name> args='run --select ...'`
- **Orchestrated by a Task** calling `EXECUTE DBT PROJECT` → dbt becomes part of a normal task graph
- Snowsight for edit/run/DAG/logs; Git via API integration to GitHub/GitLab
- Runs under Snowflake RBAC; lineage flows into Horizon
- Post-dates the current exam guide

### How the layers stack
Openflow (ingest) → Streams (detect change) → Tasks (orchestrate) → managed dbt (transform)
