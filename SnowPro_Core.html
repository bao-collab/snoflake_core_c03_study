Domain 1：架构与核心特性（31%，最重）

三层架构

层 做什么 计费 关键点
Cloud Services 协调 / 大脑：认证与 RBAC、查询解析与优化（决定剪枝哪些 micro-partition）、元数据管理、事务管理、基础设施管理 超过当日计算用量 10% 的部分才收费 元数据缓存 + Result Cache 都住在这里
Compute（Virtual Warehouse） 执行 / 动手：跑查询 按 credit/秒计费，最少 60 秒 各 warehouse 之间完全独立，互不影响性能；Local Disk (SSD) Cache 在这里
Database Storage 存：列式压缩存储在云对象存储（micro-partition） 按压缩后的 TB/月 用户无法直接访问底层文件

★ 口诀：服务层动脑，仓库层动手，存储层躺平。

题干出现 coordinates/manages/optimizes/authenticates → Cloud Services（协调者）；executes/processes the query → Compute；stores/compressed/columnar → Storage。

⚠️ 易放错：Result Cache 和元数据都在 Cloud Services（命中时不需要 warehouse）；只有 Local Disk/SSD Cache 在 Compute。micro-partition 拆两半：元数据（MIN/MAX、剪枝用）在 Cloud Services，物理数据（压缩字节）在 Storage——physical storage/actual data → Storage，metadata about/statistics → Cloud Services。

⚠️ execution PLAN ≠ execution：生成计划（optimizer：解析、分区裁剪、JOIN 顺序）在 Cloud Services；执行在 Compute。看到 execution 先看后面有没有 plan。

★ 三层里只有 Compute 用户可配置，另两层全托管——问 which layer can the user configure → Virtual Warehouse。「用它」≠「配它」：建角色/看 History 是消费服务；改 WAREHOUSE_SIZE/AUTO_SUSPEND/multi-cluster 才是调参数。原因：计算层是你租用的弹性资源，按需付费必须可调；Storage/Cloud Services 是托管承诺。

必记：三层是"存算分离 + 服务解耦"。这是 Snowflake 所有优势（弹性、并发隔离、零拷贝克隆）的根源。看到题目问"为什么两个团队互不影响"→ 独立 warehouse。

★ 产品定位题（送分）：三支柱 = Performance / Concurrency / Simplicity，正好是三层架构的三个推论——存算分离→性能，多仓库互不抢资源→并发（最有辨识度的一条，传统数仓的痛点就是「ETL 一跑 BI 就卡」），全托管、无需调索引/分区/vacuum→简单。

口诀：快、并、简 —— 云上专有，不落地不开源。

排除法：选项里出现 on-premise / open source / self-managed 等传统 IT 或开源阵营的价值观，直接排除——那是竞品（Databricks、Trino、ClickHouse）的卖点，与 Snowflake 定位相反。Snowflake 是纯云原生 + 专有闭源，只跑在 AWS / Azure / GCP 上。

分界线是动机：脱敏 = 我自己想保护数据（Enterprise）；合规认证 = 法律要求我必须达标（Business Critical）。

★ 四档一句话：标准版给门禁，企业版会切片，关键版扛合规，VPS 独占楼。 门禁 = 对象级 RBAC、MFA、SSO、Network Policy｜切片 = 列级/行级安全、多集群、MV、SOS/QAS、90 天 TT、ACCESS_HISTORY｜合规 = HIPAA/PCI、Tri-Secret、PrivateLink、Failover｜独占楼 = VPS 完全隔离。

看到 dedicated/isolated/not shared with other customers → 一律 VPS。⚠️ "有自己的" ≠ "专属的"：Standard 也有自己的 metadata store，但是逻辑隔离（同 Cloud Services 上跑）；VPS 才是物理独占（公寓 vs 整栋楼）。
⚠️ VPS = Virtual Private Snowflake，不是你的 VPC——Snowflake 纯 SaaS，任何版本都跑在自己云账户里，从不部署进客户 VPC。PrivateLink 同理：只是私有通道，Snowflake 依然在它自己那边。

⚠️ 「object-level access control」不是高级功能——它就是 GRANT SELECT ON TABLE … TO ROLE … 这套 RBAC，Standard 就有，否则连基本用户隔离都做不到。名字里带 "control / security" 不等于要付费。

⚠️ 问 "only available in Enterprise or higher" 时，Business Critical 独有的功能不算（如 Tri-Secret Secure——它在 Enterprise 版不可用）。选项里同时出现 Enterprise 功能和 Business Critical 功能时，选恰好从 Enterprise 起步的那个。

⚠️ SOC 2 是公司层面的认证，不挂钩版本；挂钩版本的是 HIPAA / PCI（Business Critical）。

★ 加密本身按版本分三层，别看到"加密"就跳到 Business Critical。

自动加密（静态数据）→ Standard 就有，全版本默认开启，不用配置。
Periodic rekeying（密钥定期自动重新加密）→ Enterprise 起——这不是"是否加密"，是加密之上的密钥自动化管理增值功能，密钥仍由 Snowflake 管理。
客户参与管理密钥（Tri-Secret Secure，客户自带密钥 + Snowflake 密钥合成根密钥）→ Business Critical 起。

⚠️ 判据不是"加不加密"，是密钥由谁管、管到多细：Snowflake 自己按周期轮换 → Enterprise；客户参与密钥管理 → Business Critical。
自检句式：这个功能是基础能力，还是在基础能力之上的自动化/治理增强？出现 automatic / periodic / policy / advanced 这类修饰词，基本不在 Standard。

★ 先读问法：available with Enterprise ≠ only in Enterprise。

问法含义Standard 就有的功能

only available in / exclusive to / requires / minimum edition是不是恰好从这一档起步❌ 不算

版本是向上累积的：Standard ⊂ Enterprise ⊂ Business Critical ⊂ VPS。所以 available with Enterprise 的正确答案集 = Standard 的 + Enterprise 的，只排除 Business Critical 及以上。Geospatial（GEOGRAPHY/GEOMETRY）是 Standard 起就有的,在这种问法下照样是对的。

⚠️ 选项把两个功能捆在一起时，按门槛最高的那个算。replication and failover：单纯 replication 是 Standard，但 failover / failback 要 Business Critical——只要 failover 这个词在，整条就被抬到 Business Critical。读到 and 就拆开分别定档。

⚠️ 「index」是 Snowflake 里的绝对假词——没有索引这个概念，靠微分区 + 元数据剪枝替代。index / automated index management 出现即淘汰。

Virtual Warehouse

  • 尺寸：XS → 4XL/6XL，每上升一档服务器数和 credit/小时都翻倍（见下表）
  • Scale UP（改大小） = 解决单个查询慢、复杂查询、数据溢出
  • Scale OUT（多集群，加集群数） = 解决并发排队（queuing）
  • 计费：启动后最少收 60 秒，之后按秒。调整大小不影响正在运行的查询，只对新查询生效。
  • Auto-suspend 默认 600 秒（Snowsight 建表时常设 5–10 分钟）。挂起会清空 warehouse 本地缓存。
  • Auto-resume：有查询进来自动启动。
  • 多集群模式：
  • Maximized（min = max）：一直全开，用于可预测的高并发
  • Auto-scale（min < max）：按需增减
  • Scaling policy：Standard vs Economy，见下方 ★ 口诀
  • Snowpark-optimized：内存/CPU 加强，用于大内存的 ML / Snowpark 工作负载

★ Warehouse 权限四件套（只能授给 Role，不能给 User）：MODIFY=改属性（size/参数）；OPERATE=管开关（start/suspend/resume/abort 查询）；USAGE=能用它跑查询；MONITOR=看查询历史/用量。口诀：「修改」动配置，「操作」动状态——别把 OPERATE 当成能改 size。

★ Standard 快启快停（忙就加/闲连续 2–3 次检查就关，≈2–3 分钟）；Economy 慢启慢停（攒够 6 分钟才启，闲连续 5–6 次检查才关，防抖动 flapping）。

口诀：Economy 六分钟起步收工，Standard 两三分钟走。

★ 多集群模式不是「选项」，是 MIN/MAX 两个数字的关系隐式决定的。Snowflake 没有任何「模式」字段可填 —— 决定它的只有 MIN_CLUSTER_COUNT 和 MAX_CLUSTER_COUNT。
（WAREHOUSE_TYPE 确实存在，但它的值只有 STANDARD / SNOWPARK-OPTIMIZED，与多集群无关——别被这个真参数名骗过去。）

口诀：min ≠ max 会伸缩，min = max 全打开。

⚠️ 排队时该调 MAX_CLUSTER_COUNT，不是 MIN_CLUSTER_COUNT：MIN 是底薪——常驻集群数，闲时也照烧 credit；MAX 是上限——排队时按需自动开，闲时自动缩回。提高 MIN 也能"消除"排队但是浪费钱，不是 recommended way。唯一该调高 MIN 的场景：负载可预测、持续高并发、不想要冷启动延迟（如每天固定时段的 BI 高峰）——这时候 Maximized（MIN=MAX）反而合理。

★ 缩容（scale in）关的是最闲（least-loaded）的集群，不是最忙的。最闲集群上查询少，能挪去别的集群（redistribute）；最忙的正在扛大量查询，关了挪不动。

设置模式行为
MIN ≠ MAX（如 1 和 5）Auto-scale按排队负载动态增减集群
MIN = MAX（如 5 和 5）Maximized启动即全开 5 个，不增不减

⚠️ 干扰项套路：虚构参数 —— 把一个模式名包装成能填进某字段的枚举值。选项里出现你没在文档见过的参数名，先怀疑它根本不存在（同类：编造的视图名、编造的 warehouse type）。

★ 最狠的一个干扰项：Auto-resize（不存在）。Snowflake 永远不会自动改 warehouse size，它只会自动增减集群数。

口诀：只有 suspend / resume 带 auto；size 靠手动，cluster 靠 min-max。

★ 计费看「状态」，不看「忙不忙」：idle / inactive ≠ 免费。只要仓库是 running，节点已分配、已开机待命，照扣 credit。

口诀：开着就烧钱，挂起才停表 —— 关键看 suspended，不看忙不忙。

⚠️ 判断题里出现 idle / inactive 而没说 suspended，默认就是「开着但没活干」→ 照收费。这也正是 AUTO_SUSPEND 存在的意义：问「怎么控制仓库成本」→ 答案基本都指向 AUTO_SUSPEND + AUTO_RESUME。

★ Resize 默认异步：ALTER WAREHOUSE … SET WAREHOUSE_SIZE= 命令立刻返回，新节点在后台 provisioning。WAIT_FOR_COMPLETION = TRUE 让命令/会话挂起等仓库就位，不是反过来"仓库等查询"。方向记反是本题最常见坑。

用途：脚本里确保下一条大查询开始前 resize 真的完成了。⚠️ 与此无关的默认行为：resize 时正在跑的查询不受影响，继续在旧节点跑完，新 size 只对之后的查询生效。

什么时候该「关掉」auto-suspend

关掉 = 永远不停 = 一直烧 credit，所以只有「常热的收益 > 常烧的成本」时才关。官方只给两个理由：

口诀：关挂起，两个理由 —— 不停的活、不等的人。（steady workload / no lag time）

场景该怎么做为什么
steady workload（持续不断有查询）关 auto-suspend本来就闲不到挂起，留着只会「刚挂起又被唤醒」抖动，成本上不吃亏
要求零延迟 / 无冷启动（BI 仪表盘、实时应用）关 auto-suspend恢复有几秒 provisioning，且 SSD 缓存清空，前几个查询明显变慢。宁可多花钱保住热缓存 —— 这是最核心的一条
用户在 24/7 期间的不同时间（at different times）用开 auto-suspend❌ 方向相反的干扰项：different times = 中间大量空档，正是该自动挂起省钱的时候
不想每次都手动开仓库开 AUTO_RESUME❌ 答非所问：这是另一个参数，与 auto-suspend 无关

⚠️ 陷阱设计：24/7 让人误读成「全天候 → 不能停」。真正的关键词是前面的 different times（错峰、间断），不是 24/7。
一字之差：different times = 断断续续 → 开挂起；steady = 持续不断 → 关挂起。

配套记：错峰用 → 开挂起；说「手动」→ 那是 resume。

参数作用关闭的后果
AUTO_SUSPEND闲置 N 秒后自动挂起一直烧钱，但永远热

存储：Micro-partitions & Clustering

  • Micro-partition：Snowflake 自动创建，每个 50–500 MB 未压缩数据，列式存储，不可变（immutable）
  • 每个 micro-partition 的元数据记录：该分区内所有列的 min/max 值、distinct 数量、NULL 数量，以及行数与未压缩字节数
  • Pruning（剪枝）：查询时靠这些元数据跳过不相关分区 —— 这是 Snowflake 性能的核心机制
  • Clustering：数据天然按加载顺序聚集。表很大（多 TB）且查询总按某列过滤时，才考虑定义 clustering key
  • Automatic Clustering 是后台服务，消耗 credit（serverless），不占用你的 warehouse
  • 判断是否需要重聚簇：SYSTEM$CLUSTERING_INFORMATION，看 average_overlaps / average_depth（depth 越小越好）

别选错：clustering key 应选低到中基数且常用于 WHERE / JOIN 的列。选高基数列（如 UUID）是错误答案。

★ Pruning = 排除/跳过/不读取，不是"利用"什么。优化器看 micro-partition 元数据（MIN/MAX），确定肯定不含目标数据 → 直接跳过。选项说"利用分区重叠" → 方向反了，剪枝要的恰恰是重叠少。

★ 聚簇看 TB，小表别折腾——门槛 multi-terabyte，记不住数字就选最大单位。原因：Automatic Clustering 持续烧 credit，收益要盖过成本才划算。

⚠️ 「分区」≠「排序」：微分区默认按写入顺序存放，不排序；Clustering Key 只是让同值行少落几个分区，不是分区内排序。

⚠️ "benefits of micro-partition" 先分事实 vs 好处：不可变/按写入顺序存是机制事实；剪枝快、免索引、支持 TT 才是真正的 benefit。选项把机制包装成好处（如"数据自动排序"）先查真假再查算不算优点。

四条同时满足才建说明
表在多 TB 级别硬门槛
查询经常按某列过滤 / JOIN聚簇列要选对，否则白建
读远多于写写多 → 反复重排 → 成本爆炸
当前剪枝确实差先用 SYSTEM$CLUSTERING_INFORMATION 验证，本来就低就别建
  • 聚簇列最多 3–4 列，再多收益递减、成本上升；顺序按基数从低到高（先粗后细）
  • 高基数列用表达式降基数：CLUSTER BY (TO_DATE(ts))，而不是直接用秒级时间戳

★ 基数是一段区间，两头都排除：极低（M/F、Y/N）❌ · 低到中 ✅ · 极高（UUID、秒级时间戳）❌。

判据：剪枝要「一个值只落在少数分区里，且一个分区只覆盖少数值」。只有两个值 → 几乎每个微分区都同时含 M 和 F，查哪个都得全扫，剪不掉；UUID 全唯一 → 排序也无法把范围收紧，且重排成本无穷。两头失效的机制不同，但结论都是 ❌。

信号该加 Clustering Key？为什么
大表上查询逐渐变慢✅ 症状信号剪枝效率在下降
clustering depth 大 / overlaps 多✅ 量化信号同一个值散落在很多微分区里
微分区数量少❌ 正好反了分区少 = 表小 = 本来就没多少可剪；要分区多才值得
DML 被阻塞 / 等待❌ 完全无关那是锁竞争，和数据物理排布无关；加聚簇反而增加后台重排负担

⚠️ 本题的错法是「记住了相关，记反了方向」。基数相关 → 误记成「越低越好」；分区数相关 → 误记成「越少越要」。
解法：每条判据都配一个「为什么」，方向就锁死了——「小表本来就剪得动」这句一想起来，就不可能选「微分区少时用」。只背结论的知识点，考场上是可以被翻转的。

★ 和另外三个性能工具串起来：Clustering 是唯一改变数据物理排列的，其余三个都是加「外挂结构」或「借算力」。
版本差异也是考点：Clustering 所有版本可用；SOS / MV / QAS 都要 Enterprise。

★ 口诀：元数据 —— 全列全分区，自动免费。「Snowflake 自动为所有微分区的所有列收集元数据」是 True。
⚠️ 这是「绝对化表述」少见的例外：平时 all / every / always 多半是陷阱，但这条必须是全覆盖——没有索引，剪枝全靠元数据，漏一列那列就没法剪枝。免调优的根基就在这里。

反过来：看到 “需要手动 ANALYZE / 建索引 / 收集统计信息” → 一定 False。

元数据 vs 聚簇（别混）：元数据收集=自动、全列、无需配置、免费，永远存在；Clustering Key=手动指定，改变数据在分区间的物理排列，让 MIN/MAX 范围更紧凑。
一句话：元数据永远在，聚簇只是让元数据更有效——没聚簇时分区值域重叠严重，剪枝就差，这正是 average_overlaps 要看的东西。

视图类型

  • Standard：只是存了个查询定义，每次执行
  • Materialized：预计算并持久化结果，自动后台维护（消耗 serverless credit），Enterprise+，限制多（只能查单表、不支持 JOIN / UNION / 大部分聚合之外的操作）
  • Secure：隐藏视图定义（GET_DDL 看不到），且绕过某些查询优化以防数据泄露 → 因此性能比标准视图差。共享数据时必须用 secure view

★ Secure View 的两个代价，一隐私一性能，成对出现：① 视图定义对非 owner 隐藏（GET_DDL / SHOW VIEWS 看不到 SQL 文本）；② 优化器被限制 → 比普通视图慢。

两者是同一个原因的两面：防止推断出未授权的行。普通视图会把 WHERE 谓词下推到底层表、会因错误信息/执行顺序泄露被过滤掉的行的存在；Secure View 先做安全过滤再谈优化，谓词下推和分区裁剪都被削弱——安全是靠「少优化」换来的。

⚠️ 它不做的事：不加密数据、不做行级/列级策略、不省存储、不改权限模型。Secure 只管「别让人反推出来」这一件事。要遮列值用 Masking，要限行用 Row Access Policy——见上面的粒度阶梯。

Domain 2：账户管理与治理（20%）

RBAC（角色访问控制）

核心原则：权限授予角色，角色授予用户/其他角色。用户不直接拥有权限。

系统角色层级（从上到下继承）：

ORGADMIN            组织层，独立在下面这棵树之外！
────────────────────────────────────────
ACCOUNTADMIN        账户内顶层，包含 SYSADMIN + SECURITYADMIN
├── SECURITYADMIN   管理用户、角色、全局授权（继承 USERADMIN）
│   └── USERADMIN   创建/管理用户和角色
└── SYSADMIN        创建/管理数据库、warehouse 等对象
    └── PUBLIC      默认角色，所有用户自动拥有

最佳实践高频考点： - 自定义角色应授予 SYSADMIN，这样 SYSADMIN 才能管理所有对象 - ACCOUNTADMIN 应尽量少人拥有，且必须启用 MFA - 只有 ACCOUNTADMIN 能看到账单、创建 Resource Monitor、管理 reader account - Secondary roles：一个会话中可同时激活多个角色的权限（USE SECONDARY ROLES ALL） - Database roles：作用域限定在某个数据库内，不能授予账户级对象权限，主要用于共享场景（share 里可以包含 database role，用于给消费者做细粒度授权） - ⚠️ Secondary roles 的坑：激活多个角色只是权限并集；创建对象时 owner 仍然是 primary role。场景题爱考这一句

访问对象需要的权限链：要查一张表，需要 database 的 USAGE + schema 的 USAGE + table 的 SELECT + warehouse 的 USAGE。缺一不可 —— 这是常考的"为什么用户看不到表"。

Ownership：每个对象有且仅有一个 owner 角色（DAC 部分）。GRANT OWNERSHIP 可转移。

★ 建完自定义角色的下一步固定动作：GRANT ROLE <custom> TO ROLE SYSADMIN;——问 after creating a custom role, what should be done，答案永远是这句。

方向别记反：GRANT ROLE child TO ROLE parent，父继承子。所以「挂到 SYSADMIN 下」= 把自定义角色 grant 给 SYSADMIN，不是反过来。被授予的一方是上级。

为什么必须挂：SYSADMIN 的定位是能管账户内所有对象。不挂 → 自定义角色拥有的对象 SYSADMIN 看不见也管不了，角色树上出现孤儿分支，只有 ACCOUNTADMIN 能穿透；一旦持有者离职，管理链就断了。挂上去，整棵树重新完整。

⚠️ 时序陷阱：题干写 after creating，那所有描述「创建时该用谁」的选项（如「用 SYSADMIN 创建」）直接出局——它们不是错答案，是在答另一个问题。先用题干的时间词筛掉整类选项，再在剩下的做排除法。

⚠️ 挂给 PUBLIC / 挂给 ACCOUNTADMIN 都是错的：PUBLIC 人人都有，等于把权限发给全账户；ACCOUNTADMIN 已经继承 SYSADMIN，挂那儿等于绕过正常管理层。

★ Snowflake 访问控制 = RBAC + DAC 两个模型的混合。问 which models does Snowflake use → 就这两个。

模型全称在 Snowflake 里体现为
RBACRole-Based权限给角色、角色给用户；用户不直接持权限
DACDiscretionary（自由裁量的）每个对象有 owner，owner 可自主决定把权限 grant 给谁

合起来一句话：对象由角色拥有，该角色自主向其他角色授权，用户通过角色获得一切。「角色拥有」是 RBAC 的部分，「自主授权」是 DAC 的部分。

⚠️ IAM / ACL / MAC / ABAC 出现在这类选项里一律排除。IAM 尤其眼熟（AWS 的东西），但它是云厂商的身份服务，不是 Snowflake 的访问控制模型。眼熟不是证据 —— 认得 RBAC 不等于另一个就该选眼熟的。

★ 口诀：用户只借身份，角色才是主人。权限和所有权只挂在 role 上；user 唯一能被授予的东西是 role 本身。

做题技巧：看到 ownership / privilege 的判断题，先扫主语宾语是 user 还是 role，往往不用读懂题意就能判。

★ 创建账户 = ORGADMIN，不是 ACCOUNTADMIN。名字有误导性：ACCOUNTADMIN 是「一个账户内部的最高权限」，不是「管理多个账户的权限」。

比喻：总统权力再大也不能创建新国家——建国是更高一层的事。ORGADMIN 站在 Organization 层，下面挂着 Account A / B / C，每个账户里各有自己的 ACCOUNTADMIN。

⚠️ ORGADMIN 反过来也够不着账户内的数据对象（表、schema、warehouse 一律看不到）。这是刻意的职责分离：ORGADMIN 管行政，ACCOUNTADMIN 管业务——两边都不是对方的超集。

信号词：create an account / across accounts / organization / ORGANIZATION_USAGE → ORGADMIN；账单、Resource Monitor、reader account、账户内一切 → ACCOUNTADMIN。

认证

  • MFA：Duo，内置，账户级免费。可用 MINS_TO_BYPASS_MFA 临时绕过
  • Federated / SSO（联合身份验证）：把验证委托给外部 IdP（Okta / Azure AD / ADFS / Ping），IdP 验证后发一张 SAML 2.0 断言给 Snowflake。好处是单点登录：一套账号登所有系统，离职时在 IdP 一关，全部同时失效。
    ★ 先拆词：federated = 「联邦制」= 认证权外包给别人。看到这个词就等于看到 SSO / IdP / SAML——问 the purpose of federated authentication，答案就是 enable SSO，不必再想。
    角色分工（考题会直接问）：IdP = Identity Provider（Okta 等，管认证）；Snowflake = Service Provider (SP)，只接受断言。Snowflake 永远是 SP，不会是 IdP。
  • Key-pair：用于服务账户/自动化，2048-bit RSA，支持轮换（可同时配两个公钥）
  • OAuth：Snowflake OAuth 或 External OAuth
  • Network Policy：IP 白名单/黑名单，黑名单优先于白名单。可设在账户级或用户级，用户级优先。创建者：ACCOUNTADMIN + SECURITYADMIN（SYSADMIN 管对象不管安全策略，没份）。
  • PrivateLink（Business Critical 起）：在你的 VPC 里建 endpoint，流量走云内网直达 Snowflake，不经公网。
    ⚠️ 它连的是 VPC，不是本地机房。题干出现 “connect from an on-premise data center” → False：本地到 VPC 那一段要靠 Direct Connect / Site-to-Site VPN，是两段拼起来的，功劳不能全算给 PrivateLink。

★ SSO 的两个高频 False 陷阱，都在「Snowflake 收到了什么」上：

① 「Snowflake 接收/存储用户的 credentials（密码）」= False。IdP 发回来的是 SAML 断言——只说「这个人是谁、已验证通过」，不含密码。密码只存在 IdP 一处，这正是 SSO 的安全价值；Snowflake 若真收密码，SSO 就毫无意义。

② 「SSO 会把用户 load / sync 进 Snowflake」= False。Snowflake user 必须事先存在（CREATE USER … LOGIN_NAME='x@company.com'），SSO 只拿断言里的 LOGIN_NAME 去匹配；匹配不上就登录失败。自动建号/停用是 SCIM 干的，和 SSO 是两个独立机制。

口诀：SSO 只送通行证，不送密码，也不送人 —— 送人的是 SCIM。

机制干什么
SSO / Federated Auth（SAML 2.0）验证「你是谁」（authentication），密码留在 IdP
SCIM同步用户与组，自动创建/停用 Snowflake user（配 Okta / Azure AD）

治理功能

  • Dynamic Data Masking：列级，基于查询者的角色返回脱敏值（masking policy）
  • Row Access Policy：行级，控制哪些行可见
  • External Tokenization（Enterprise 起）：用 masking policy 调外部厂商的 API做令牌化 —— 把真实值换成无意义的替代值（4111-1111-… → TKN-8x92kd），真值存在外部保险库里。
    ⚠️ 与加密的区别：token 和原值没有数学关系，无法反推，只能查保险库还原；加密则是可用密钥解开。题干出现「替换成无意义的值 / 外部保险库 / 不可逆推」→ tokenization，不是 encryption。代表厂商 Protegrity（其余同类：ALTR、Baffle）
  • Object Tagging：给对象打标签，可与 masking policy 结合（tag-based masking：给标签绑定策略，所有打了此标签的列自动脱敏）
  • Data Classification：自动识别并标记 PII 等敏感列（注意与 object tagging 区分 —— 官方样题就考了这个）
  • Access History / Object Dependencies：数据血缘

次判据：名字里有 policy 的东西没有一个是自动的——policy 必须先 CREATE 再 ALTER … SET 绑上去。

⚠️ 表 owner ≠ 能改 Masking Policy：谁能改表和谁能改策略是两套独立权限——表归表 owner 管，策略归策略的 owner或有 APPLY MASKING POLICY 的角色管。「我是这张表的 owner」不能过度推广成「表上绑的一切我都能改」。

额外占存储为什么

Fail-safe✅ 占TT 之后再留 7 天

判据：只有「保留了数据的历史副本」才占存储。加密、密钥管理、权限策略都是对同一份数据做事，一个字节都不多。

⚠️ 刚做过一道同选项的题时，最容易把上一题的轴带过来。「自动生效」和「占存储」在这组选项上几乎正交——加密两样都沾一半（自动 ✅、占存储 ❌）。看到熟悉的选项组，先重读一遍问句。

技术差异：External Tokenization 依赖 External Functions（要配 API Integration 指向 AWS Lambda / Azure Function），Dynamic Masking 不需要任何外部组件——这是两者最大的实现区别。
★ External Function = 在外部执行的函数，不是「从外部取数据」。它是个 SQL 函数，但函数体不在 Snowflake 里——调用时经 API Integration 把参数发给 AWS Lambda / Azure Function，拿返回值当结果。
⚠️ 「把外部数据搬进来」是 COPY INTO / Snowpipe / External Table 的地盘，和函数无关。function 的语义永远是「算」，不是「搬」。
判据：external 修饰的是紧跟其后的那个名词——External Function → 代码在外部；External Table → 数据在外部；External Stage → 存储位置在外部。先定名词，再定 external 说的是什么在外面。
分类题：External Function 本质是 UDF 的一种（只是函数体搬到了外部）——选项说"stored/defined inside Snowflake"是反的，那是普通 UDF 的特征。
安全含义：真值从未进入 Snowflake，即便账户被越权访问，拿到的也只是无意义 token。与 Business Critical → HIPAA/PCI 是互补的两层：那是平台级加密合规，这是字段级值替换。

Directory Table & 服务端加密（SSE）考纲 3.1 点名 · 题库可能还没出到

概念要点
Directory Table不是一种独立的表，而是 stage 上的一层文件元数据目录（文件名、大小、最后修改时间、FILE_URL）。建 stage 时加 DIRECTORY = (ENABLE = TRUE)，用 SELECT * FROM DIRECTORY(@stage) 查
用途管理非结构化数据（unstructured data）的入口——先在 directory table 里查到文件，再用 GET_PRESIGNED_URL / scoped URL 访问
刷新不会自动实时更新：ALTER STAGE … REFRESH，或配 自动刷新（云事件通知）
权限没有独立权限可授予——依附于 stage，能不能查 directory table 看 stage 的 READ 权限
Server-side encryption（SSE）external stage 上的选项：SNOWFLAKE_SSE / AWS_SSE_S3 / AWS_SSE_KMS 等。只有 SSE 加密的文件，Snowflake 才能生成 scoped URL / presigned URL 让你直接访问；client-side 加密的不行

★ 「非结构化数据怎么在 Snowflake 里查/给权限？」→ 答案链条是：Stage + Directory Table + URL 函数。三种 URL：FILE_URL（永久，需权限）· SCOPED_URL（临时，24h，跟当前用户绑定）· PRESIGNED_URL（临时，浏览器可直接开）。唯一不需要登录 Snowflake 的是 Pre-signed URL（发外部人/嵌 BI 报表用这个）；Scoped 和 File URL 都要 token/权限，本质是"给已登录的人用"。

★ 最高频的一条：PUT / GET 只对 internal stage 有效。External stage 要用云厂商自己的工具上传下载。

口诀：PUT 上 GET 下，只走内部台；COPY 双向跑，内外通吃。视角站在「本地机器」：PUT=推上去=上传，GET=拿下来=下载。⚠️ into a stage（PUT）≠ into a table（COPY INTO）——读到 "into" 先看后面是 stage 还是 table。本地与表永远不能直连，Stage 是唯一中转站。

⚠️ PUT/GET 跑不了 Snowsight：要读写本地磁盘，浏览器沙箱不允许 → 只能走客户端（SnowSQL / Snowflake CLI / driver）。「UI 有上传按钮」≠「UI 能执行 PUT 命令」，两者是不同机制，题干问 command 能在哪跑时别被"我见过上传功能"带偏。

口诀：内部存储 Snowflake 收，外部只给地址——External stage 只是指针+凭证，Snowflake 从没持有数据，但计算费照收（COPY 用你的 warehouse、Snowpipe serverless）。★ 看到 External 开头的对象先默念「数据不在 Snowflake 手里」——不收存储费、无 Fail-safe、TT 受限，很多题秒答。

COPY INTO

  • 加载文件大小最佳实践：压缩后 100–250 MB。太小 → 开销大；太大 → 无法并行且失败重试代价高
  • COPY 会记录已加载文件的元数据，默认 64 天内不会重复加载同一文件（除非 FORCE = TRUE）
  • 并行度取决于 warehouse 大小：每个节点可并行处理约 8 个文件。文件数少于线程数时，加大 warehouse 没用。★ 目标状态：文件数 ≥ 仓库总线程数，且每个文件 100–250 MB——两个条件缺一不可。100–250 MB 不是拍脑袋的数：它是「摊薄单文件开销」与「文件数够喂满线程」之间的交点。太小 → 线程都在开关文件而不是搬数据；太大（如 5 GB 单文件）→ 不可拆分，只有一个线程干活，并行度归零
  • 数据清洁度也是「加载最佳实践」的一部分：⚠️ CSV 数值列里带千位逗号（1,234.56）会被解析器当成字段分隔符 → 列错位或类型转换失败。数字要在源头写成 1234.56。同族的还有：日期格式统一、NULL 用统一标记（配 NULL_IF）、字段内含分隔符要加引号（配 FIELD_OPTIONALLY_ENCLOSED_BY）
  • 「文件太多太小怎么办」→ 在上传 stage 之前合并；文件太大则先 split。问题在你那侧解决，不是靠 COPY 参数。另配合按逻辑路径组织 stage 目录（/年/月/日/）+ COPY 的路径前缀过滤，减少扫描量
  • ⚠️ logical path（前缀定位目录）比 PATTERN=正则快：path 直接定位到目录只列那部分文件；PATTERN 要先列出 stage 全部文件再逐个正则匹配，文件越多越慢。「MOST efficient」类题优先选路径
  • 错误处理：ON_ERROR = CONTINUE | SKIP_FILE | SKIP_FILE_n | ABORT_STATEMENT（默认，批量加载）
  • Snowpipe 的默认是 SKIP_FILE
  • VALIDATION_MODE 用于试跑检查错误而不实际加载
  • VALIDATE() 函数查看已完成 COPY 的错误
  • 卸载（unload）默认生成多个文件；SINGLE = TRUE 强制单文件（有 5 GB 上限）；MAX_FILE_SIZE 控制大小

VALIDATION_MODE vs ON_ERROR（极高频，选项只差一个词）

口诀：VALIDATION = 只体检，不入院。跑完之后表里一行数据都没有，只返回一份「如果真加载会遇到哪些错」的报告。
想要「边加载边跳过坏行」→ 那是 ON_ERROR，不是 VALIDATION_MODE。

⚠️ 选项只差一个词，看清楚：
❌ “while completing the load” = 边加载边校验 → 这是 ON_ERROR = CONTINUE
✅ “without completing the load” = 完全不加载，只报错 → 这才是 VALIDATION_MODE

VALIDATION_MODE 取值返回什么
RETURN_n_ROWS唯一返回数据的：返回前 n 行（用来预览数据长什么样），遇错即报
RETURN_ERRORS所有文件中的所有错误
RETURN_ALL_ERRORS同上，外加之前 COPY（ON_ERROR=CONTINUE）跳过的错误行
  • VALIDATION_MODE 是 COPY INTO <table> 的参数，只用于入库；COPY INTO <location>（卸载）不支持
  • 它与 stage 的 DDL 无关——创建 stage 时没有这个选项（常见干扰项）
  • ★ 与带转换的 COPY 互斥：COPY INTO t FROM (SELECT $1, $2::DATE … FROM @stage) 再加 VALIDATION_MODE → 直接报错。原因：验证模式只「解析文件 + 按目标表结构做类型校验」，而带转换要真正启动一条 SELECT 计算管道——两条执行路径不同，验证模式没有执行表达式的能力。这是本参数唯一的「语句本身报错」情形
  • ⚠️ 「什么情况下 COPY 会返回错误」这类题，先分清数据层面还是语法/功能层面。坏行、类型不符、文件重复——那些是 VALIDATION_MODE 正常干活（它的职责就是报告数据问题），不叫「语句返回错误」。只有功能不兼容才让语句本身失败。
  • ⚠️ 文件名重复不是错误，是设计特性：COPY 的 load metadata 64 天内自动跳过同名文件（Snowpipe 是 14 天），要重载用 FORCE = TRUE。超过 64 天后同名文件会被重新加载——这才是真正的坑。
  • ⚠️ 去重的判定单位是整份文件，不是文件里的某些行/某类数据。load metadata 记录的是「这个文件名 + 这个 stage 路径」有没有被处理过，不会去看文件内容是否发生了局部变化。选项描述"部分新数据/新行"这种行级颗粒度时要警惕——真实机制只在文件级判断加载过没有，读题时把颗粒度先对齐，别被"都在说新数据"这种表面相似带过去。
  • 三件套的时序：VALIDATION_MODE = 加载之前预检 · ON_ERROR = 加载当中的容错策略 · VALIDATE() 表函数 = 加载之后回看（SELECT * FROM TABLE(VALIDATE(t, JOB_ID => '_last'))）。前 / 中 / 后各一个，常被放一起考。

半结构化数据

★ 半结构化类型只有三兄弟：VARIANT（万能容器，可装任何类型，含 OBJECT/ARRAY 本身）· OBJECT（键值对，JSON 的 {}）· ARRAY（有序列表，JSON 的 []）。就这三个。

⚠️ VARCHAR 是结构化类型，不在其中。你可以把一段 JSON 文本塞进 VARCHAR，但它就只是一坨字符串——不能用 : 路径语法查，得先 PARSE_JSON 变成 VARIANT。「能装 JSON」≠「是半结构化类型」。

判据：能不能用 : 取字段。能 → 半结构化；不能 → 只是字符串。TEXT / STRING / BINARY 出现在这类选项里一律排除。

⚠️ format ≠ data type，选项混装是常见陷阱：JSON/XML/Avro/Parquet/ORC/GeoJSON 是文件格式（写在 FILE_FORMAT 里）；VARIANT/OBJECT/ARRAY 才是列的数据类型（写在建表语句里）。题干问"data type"时，格式类选项直接出局。

  • VARIANT 类型，单个值上限 16 MB（压缩后）
  • 用 : 取字段（src:name），:: 转类型
  • FLATTEN / LATERAL FLATTEN 把数组展开成行
  • Snowflake 会自动为 VARIANT 中的重复字段提取元数据以提升查询性能
  • 其余工具：PARSE_JSON（字符串→VARIANT）、TRY_PARSE_JSON（安全解析）、GET_PATH（安全取值）、OBJECT_CONSTRUCT / ARRAY_AGG（反向：行→嵌套）

FLATTEN（table function）

★ 先 PARSE_JSON 再 FLATTEN，这是两步不是一步。

字符串 '{"a":[1,2]}'
   ↓ PARSE_JSON()      字符串 → VARIANT（一进一出，不产生新行）
VARIANT
   ↓ LATERAL FLATTEN() VARIANT → 多行（产生行）

FLATTEN 的输入必须已经是 VARIANT，它不吃字符串。题干出现 interpret an input string / produce a VARIANT value → PARSE_JSON；出现 expand into rows / one row per element → FLATTEN。

口诀：FLATTEN = 把「一格里的一串」变成「一串行」。一个订单里 3 个商品 → 变成 3 行。

（题库若纠结「半结构化 vs 结构化类型都能不能 FLATTEN」——考纲没有这一层，是题库自己的问题，不用记。答案是都可以。）

SELECT t.id, f.value:name::STRING AS item_name
FROM orders t,
     LATERAL FLATTEN(input => t.items) f;

KEY 给对象、INDEX 给数组，两者互斥,必有一个是 NULL。

  • 参数里只需记 OUTER（默认 FALSE）：空集合时那一行会直接消失，设 TRUE 才保留、VALUE 填 NULL。其余 PATH / RECURSIVE / MODE 认得出即可

  • Snowpipe：serverless，微批。基于云事件通知（S3 Event / Azure Event Grid / GCS Pub-Sub）或 REST API 触发。按实际计算量计费（含每千文件的开销费），不占用你的 warehouse。延迟通常 1 分钟左右，不适合真正的实时
  • Snowpipe Streaming：行级直写，低延迟，无需先落文件

★ Snowpipe 的计费粒度：per-second / per-core。后台用 Snowflake 自己管理的资源，计量单位是核（不是 XS/S/M 这种 warehouse size），按秒计费、没有 60 秒起步。另有每 1000 个文件的固定管理费——文件太碎会让这笔变贵。

口诀：Snowpipe 无仓库 → 按核按秒；手动 COPY 用仓库 → 按尺寸，60 秒起。

★ 一条通用规则：凡「serverless」类功能——Snowpipe、Serverless Task、Automatic Clustering、Search Optimization 后台维护、MV 后台刷新——一律是 Snowflake 管理的计算资源、按秒计费、不占用你的 warehouse。
排除法：题干说「按 warehouse 大小」「最低 60 秒」→ 那是普通 warehouse / 手动 COPY；说「pipe 个数」「存储桶大小」→ 都与加载费无关。

推论：CREATE PIPE 语法里根本没有 WAREHOUSE = 参数。凡是 “requires a virtual warehouse” + serverless 功能 → False。口诀：Pipe 无仓，COPY 有仓。

⚠️ dedicated（专用的）是这里的陷阱词：问「是否需要一个 dedicated warehouse」会诱导你想「那共享一个总行吧」，从而掉进「总之要仓库」。正确的否定要深一层：不是「不需要专用的」，而是「完全不需要任何 warehouse」。

★ 更强的一条推论：serverless 的尺寸你设不了。Snowflake 按实际工作量自动伸缩——凡是"让用户设 serverless 尺寸"的选项，一律排除，因为能设尺寸就不叫 serverless 了。SERVERLESS_FEATURES_SIZE 这类参数不存在。

⚠️ 唯一的例外别记混：Serverless Task 可以给一个初始规模提示 USER_TASK_MANAGED_INITIAL_WAREHOUSE_SIZE——那只是起点建议，之后仍由 Snowflake 自动调整，不是"你来定尺寸"。

  • Stream：CDC，记录表的变更（INSERT/UPDATE/DELETE）。是"偏移量指针"不是数据副本。消费（DML 中读取）后自动前进
  • 类型：Standard（含所有变更）、Append-only（仅插入，开销更小）、Insert-only（外部表用）
  • Task：调度 SQL，可用 CRON 或 interval。可串成 DAG（一个 root task + 子 task，最多 1000 个）。可用 warehouse 或 serverless。
    ★ 一个 Task = 一条 SQL 语句 + 一个调度。AS 后面只能跟单条语句，选项写 a set of SQL statements / multiple statements → False。
    想跑多条只有两条路，而这两条恰恰反证了「Task 的容量就是一条」：① 包成存储过程（CREATE TASK t AS CALL my_proc();——过程内部几十条，对 Task 仍是一次 CALL）；② 建 DAG（CREATE TASK t2 AFTER t1 AS …——多个 Task 串起来，每个仍是单语句）
  • 经典组合：Stream + Task 实现增量 ELT 管道
  • Dynamic Table：上面那套的声明式替代 —— 你只写目标查询和 TARGET_LAG，Snowflake 自动增量刷新

★ Pipe / Stream 常被当同类混选，但作用域方向完全相反：Pipe：外部文件 → 表（数据进来的入口）；Stream：表 → 下游（数据已经在表里之后，追踪变化）。

Stream 根本看不到云存储——它只挂在表/视图上，跟"文件有没有落地"毫无关系。而且 Stream 是被动的：它只是记账本（偏移量指针），自己不会触发任何加载或动作，必须由 Task 去消费它（或手动 DML 读取）才会前进。
⚠️ 题干出现"文件一到就自动处理"→ 先想 Pipe；出现"表已经变了，要追踪/响应这个变化"→ 才是 Stream（+ Task）。别因为两者都带"持续、增量"的味道就互换。

★ 考点：Snowpipe 靠 load history 按文件名去重——加载过的文件名记下来，再遇到同名就跳过。
CREATE OR REPLACE PIPE 会把 load history 清空 → 如果 stage 里旧文件还在、又被重新通知或 REFRESH，会全部重新加载 → 数据重复。
正确说法是 “previously loaded files may be reloaded”，不是 “will be ignored”（把因果反过来是常见干扰项）。

口诀：重建 Pipe，历史归零，旧文件可能再来一遍。

三种缓存（必考）

缓存 位置 存活时间 说明
Metadata cache Cloud Services 一直有 让 SELECT COUNT(*)、MIN/MAX 等不启动 warehouse就能返回
Query Result cache Cloud Services 24 小时，被复用则续期，最长 31 天 需要 SQL 文本完全一致、底层数据未变、不含非确定性函数（如 CURRENT_TIMESTAMP）。任何用户只要有权限都能命中，且完全不消耗 credit
Warehouse (local disk) cache Compute 节点 SSD warehouse 挂起即清空 缓存查询用到的 micro-partition 数据。容量正比于 warehouse 尺寸（尺寸 = 节点数 = SSD 总量）；缩小尺寸 → 节点被移除 → 那部分缓存随之消失

高频陷阱：结果缓存命中 = 零 credit + 不需要 warehouse 运行。USE_CACHED_RESULT = FALSE 可关闭（测试用）。

★ 判据只有一条：这个操作要不要碰物理数据字节？不碰 → 不要 warehouse；要读/写/算数据本身 → 要。ALTER TABLE ADD COLUMN 只改元数据，一个字节都没动——同 Zero-Copy Clone 一个原理（存算分离）。⚠️ 唯一例外：CLUSTER BY 触发的 reclustering 是 serverless（动物理排布，单独计费）。

免仓库（元数据/搬运层）要仓库（数据本体层）
所有 DDL：CREATE / ALTER / DROP / DESCRIBE / SHOWSELECT（含 MV、外部表）
PUT / GET / LIST / REMOVE（只搬文件，不解析内容）COPY INTO（要解析文件、按列写入 micro-partition）
元数据查询：COUNT(*)、MIN/MAX(col)DML：INSERT / UPDATE / DELETE / MERGE
Result Cache 命中、INFORMATION_SCHEMA存储过程、UDF 执行、CTAS

口诀：改结构不要仓，搬文件不要仓；查数据要仓，跑逻辑要仓。再细分一句：PUT/GET 只搬箱，COPY 才拆箱——拆箱（解析数据）才要人手（warehouse）。

⚠️ 建表三兄弟，按"碰不碰数据行"排序：

语句复制什么要不要仓库
CREATE TABLE B LIKE A只复制结构（列/类型/约束），B 是空表❌ 不要——从 A 的元数据"抄"定义，全程不读 A 的数据行
CREATE TABLE B CLONE A（Zero-Copy Clone）结构 + 数据，但靠 micro-partition 元数据指针，不复制实际存储❌ 不要——瞬间完成，同一原理
CREATE TABLE B AS SELECT * FROM A（CTAS）结构 + 数据，真的读 A 的数据行再写入 B✅ 要——本质是一条 SELECT

LIKE 和 CLONE 表面上都"瞬间建表"，但别混：LIKE 建的是空表（只抄结构），CLONE 建的是有数据的表（抄结构+数据指针）——两者要不要仓库的答案一样，但"复制了什么"完全不同，题干问后者时不能用前者的理由答。

★ Result Cache 命中的完整条件（七条）：

  1. SQL 文本逐字符一致（大小写、空格、注释都算）
  2. 底层表数据未变（无 DML、无 reclustering）。★ 失效粒度是「表/微分区」，不是「列」——改了 note 列，SELECT id, amount 的缓存照样失效。微分区不可变，UPDATE 会整分区重写（含所有列），Snowflake 不逐值比对，一律保守作废。记：追踪「表版本」，不是「列版本」。
  3. 不含非确定性函数
  4. 不含外部函数 / 外部表 / 非确定的 UDF
  5. 在 24 小时内（每次命中重置，累计上限 31 天）
  6. 使用者对所有底层表有权限
  7. USE_CACHED_RESULT = TRUE（默认开）

⚠️ 方向别说反：确定性函数是缓存能用的前提，非确定性才是障碍。选项写 deterministic function prevents caching → 错。
破坏缓存的是 CURRENT_TIMESTAMP()、CURRENT_DATE()、RANDOM()——每次本来就该给新值，缓存了才是 bug。
SUM()、UPPER()、ABS() 同输入必同输出，照常缓存。

⚠️ CURRENT_DATE() 非确定 vs TO_DATE('2026-01-01') 确定——写死的字面量是确定的，问"现在几号"的才不是。

★ Local Disk Cache 的大小 = 仓库尺寸：尺寸 = 节点数 = 本地 SSD 总容量（XS 1 节点 → S 2 → M 4 → L 8，每档翻倍，缓存也翻倍）。缓存物理上住在计算节点里,所以挂起全清、缩容部分丢。

⚠️ "与仓库尺寸无关"这句话只对 Result Cache 成立——它在 Cloud Services 层，仓库挂起甚至删掉都还在。这两个缓存互换就是本题的陷阱。

SSD 满了怎么办：LRU 淘汰（踢掉最久没用的微分区）。

⚠️ 缓存范围是"查询过程中访问到的列"，不是"结果集里的列"：SELECT a WHERE b 会把 a 和 b 都缓存（b 虽不在结果里，但过滤时读过），别只当成缓存最终显示的那几列。

★ Result Cache 是账户级共享，不是用户私有。A 跑过的查询，B 跑同样的 SQL 照样命中——这正是它在多人 BI 场景下的价值（同一张报表只有第一个人花 credit）。看到 only their own / per-user 一律排除。

唯一约束是权限：使用者的角色必须对底层表有足够权限（不能靠缓存绕过 RBAC）。这是安全约束，不是"只能看自己的"。

口诀：结果缓存全账户共享，只看权限不看人；RESULT_SCAN 才认本人。

RESULT_SCAN：把已执行查询的结果集当表再查——SELECT * FROM TABLE(RESULT_SCAN(LAST_QUERY_ID()))。
典型用法：SHOW TABLES 之后用它加 WHERE 过滤（SHOW 本身不支持 WHERE）；或对复杂查询结果做二次筛选而不重跑原查询（省 credit）。
⚠️ 限制：结果保留 24 小时，且只有同一用户能对自己的 query_id 用 RESULT_SCAN——这条"仅本人"是 RESULT_SCAN 的限制，不是 Result Cache 命中的限制，别混。

⚠️ 假参数警告：真实存在的是 USE_CACHED_RESULT（控制 Result Cache，默认 TRUE）；USE_METADATA_CACHE 是编造的。元数据缓存不可配置。考试惯用手法就是把真参数改一个词。

Result Cache vs 物化视图 —— 都能让"重复查询"变快，考题靠两个词区分。

★ MV 的 JOIN 限制只发生在创建那一刻。

-- 定义 MV 时写 JOIN         ❌ 报错（只能单表）

-- 建好后 JOIN 这个 MV        ✅ 完全可以

考纲 4.1 原文写的是 “Query Profile/Query insights”，两个并列。Query Insights 是 Snowsight 里的新面板：Query Profile 给你原始执行细节（要你自己看懂），Query Insights 直接把常见问题诊断出来告诉你——例如"这个查询有 exploding join""剪枝无效""用了非最优的 join 顺序"。
一句话区分：Profile = 数据；Insights = 结论。下面四条正是 Insights 会自动标出来的东西。

  • Bytes spilled to local storage：内存不够，溢出到本地 SSD → 考虑加大 warehouse
  • Bytes spilled to remote storage：更严重，溢出到远程存储 → 必须加大 warehouse 或优化查询
  • Partitions scanned / Partitions total：比值高 = 剪枝不良 → 考虑 clustering key 或改写 WHERE
  • Exploding join：输出行数远大于输入 → JOIN 条件写错（笛卡尔积）
  • Queuing：排队 → 加多集群（scale out），不是加大尺寸

★ 问 help optimize 时，只选能拧的旋钮，不选状态的副产品。

判据一句话：看完这个数字，我能对这条查询做出一个动作吗？答不上来的就不是优化点。

指标看完能做什么
Bytes scanned ↑加 clustering key、改写 WHERE、建 MV → 有动作 ✅
Partitions scanned / total ↑剪枝失效 → clustering key、改谓词 → 有动作 ✅
Bytes spilled ↑加大 warehouse → 有动作 ✅
Percentage scanned from cache ↓缓存高低取决于仓库刚不刚启动、之前跑过什么，你命令不了它 → ❌

⚠️ Percentage scanned from cache 是 Query Profile 里真实存在的字段——干扰项不靠编词，靠把「真指标」当成「优化手段」。字段存在 ≠ 它是杠杆。

硬要影响它只能调 AUTO_SUSPEND 保住 warehouse cache，但那是仓库配置层面的事，不是「优化这条查询」。

考纲 4.1 还点名了两个 ACCOUNT_USAGE 视图（在 SNOWFLAKE 数据库里，365 天保留、有延迟）：

  • QUERY_HISTORY：查过什么、耗时多久、用了哪个 warehouse。事后排查慢查询的入口
  • QUERY_ATTRIBUTION_HISTORY：把 credit 成本归因到具体查询。题眼是"哪个查询最烧钱"——注意这是成本问题不是性能问题，问"最慢"用 QUERY_HISTORY，问"最贵"用 query attribution

Workload management：把相似的工作负载分到同一个 warehouse（ETL 一个、BI 一个、ad-hoc 一个），而不是所有人共用一个。理由是 warehouse cache 只对相似查询有效，混用会互相冲掉缓存，且难以单独调尺寸和归因成本。

Materialized View 反复对大表跑同样的昂贵聚合。Enterprise+，自动维护

★ SOS 和 Automatic Clustering 管的是两件不同的事，别因为"都在性能优化里"就当同类：Automatic Clustering 动数据本身（reclustering，把相似值挪到更少的分区里，改的是"micro-partition 里的数据组织方式"）；SOS 不挪数据，只是另建一份查找用的访问路径（辅助索引），加速点查。

⚠️ 题干出现 "organization of data in a micro-partition" / "数据在分区里怎么组织" 这类措辞 → 精确指向物理排布，答案只能是 Automatic Clustering；SOS 再眼熟、再常和 clustering 放一起考，都不涉及"数据怎么摆"这件事。

★ 开启 SOS 要两个权限同时具备，不是二选一：表上的 OWNERSHIP + schema 上的 ADD SEARCH OPTIMIZATION。

判据「能力权限在对象上，成本权限在容器上」：改表的物理结构（加搜索访问路径）→ 得是表的主人；而 SOS 开了就持续烧存储费 + 后台维护 credit，所以 Snowflake 把「允许在这个 schema 里开烧钱功能」单独做成一个权限，好让更高层管理员卡住。MV、Clustering Key 是同一族的「持续烧钱」功能。

⚠️ 表上没有 MODIFY 权限。MODIFY 在 Snowflake 里确实存在，但只用于 warehouse / resource monitor / 账户级参数（GRANT MODIFY ON WAREHOUSE …）。对表做结构性变更用的是 OWNERSHIP。
这是「移植型假选项」：词是真的，位置是假的（同族：WAREHOUSE_USAGE schema）。造词干扰有两种——凭空编，和把真词挪到不存在它的地方。后者更难识破。

⚠️ 「must have which of the following」= 找全部必要条件，别在选出一个合理项后就停。问句是复数就默认不止一个。

症状 → 对策（先问"是不是 warehouse 问题"）

判断顺序：先排除 warehouse，再谈优化服务。题目给的是症状，不是"我想上哪个服务"。先看症状指向的是资源不够（内存/并发）还是访问路径不好——前者改 warehouse，后者才上服务。别一看到"慢"就往优化服务上选。

症状对策为什么
查一行 / 大表里捞极少数行Search Optimization访问路径问题
扫描量巨大但只要一部分结果QAS
同一聚合反复算Materialized View
总是按某列过滤大表（大表、写少读多）Clustering Key
扫描分区数 ≈ 总分区数（partitions scanned ≈ partitions total）Clustering Key 或 SOS；也可能是 WHERE 写法挡住了剪枝剪枝失效
查询排队（queued / QUEUED_OVERLOAD_TIME 高）多集群 scale out并发不够

最后两条最容易丢分，因为它们长得像"性能问题"，实际是资源问题：bytes spilled to local storage 出现 → 内存不够 → scale up；queued overload time 高 → 并发不够 → scale out。记住「溢出往上、排队往外」。

★ 排队的正解是加集群，不是调 MAX_CONCURRENCY_LEVEL。该参数（默认 8）只是单个集群同时跑几条查询的上限，调高它不增加任何计算资源——只是让更多查询挤进同一批节点抢内存和 CPU。排队时间是短了，每条查询自己变慢了，总吞吐没涨，还可能因内存被瓜分而 spilling，反而更差。

一句话：那是把队伍从门外挪到门内。要真正扩容并发，只有 多集群 scale out。

读图信号：Running 与 Queued 并存 → 并发不足（不是单查询慢）；排队周期性、可预测（如每天上午高峰）→ multi-cluster auto-scale（MIN≠MAX），而不是手工调大尺寸。

DML 的表锁与并发阻塞

★ 判断标准只有一句：这条命令需不需要「先找到已有的行再改它」？
需要 → 拿表级锁，同表并发会串行排队；不需要（纯追加）→ 不阻塞，可并发跑。

口诀：只加不改的不锁表。

操作是否锁表原因
INSERT✅ 不阻塞纯追加，只写新微分区
COPY INTO <table>✅ 不阻塞同上，append-only
UPDATE❌ 锁表要定位并重写已有行
DELETE❌ 锁表同上
MERGE❌ 锁表同上（最典型）
  • 微分区不可变：UPDATE/DELETE 实际是「重写受影响的微分区」，所以必须先锁定它们
  • 因此并发的多个 INSERT/COPY 可以同时灌同一张表——这正是 Snowpipe 能并行加载的前提
  • 被阻塞的 DML 会等待，超时由 LOCK_TIMEOUT 控制（默认 43200 秒 = 12 小时）

★ 一句话区分：聚合函数把多行压成一行；窗口函数行数不变，只是每行多算一个跨行的值。

口诀：GROUP BY 减行，OVER 不减行。

聚合函数（Aggregate）窗口函数（Window）
写法SUM(x) … GROUP BYSUM(x) OVER (PARTITION BY … ORDER BY …)

克隆与 Time Travel

  • Zero-copy clone：瞬时、初始不占额外存储（共享 micro-partition），改动才产生新分区。可克隆 database / schema / table
  • 不能克隆：内部 stage 里的文件（stage 对象本身会克隆，文件不复制）、指向 internal stage 的 Snowpipe、临时表 / 临时对象
  • 克隆 database/schema 会带走全部子对象：schema、table、view、stage、file format、sequence、stream、task、外部表…… ⚠️ 选项用 only schemas and tables 把范围收窄 → False
  • 权限：子对象的权限会克隆，被克隆对象自身的权限不克隆（自身的可用 COPY GRANTS 补上）
  • Time Travel：AT / BEFORE + TIMESTAMP / OFFSET / STATEMENT。UNDROP TABLE 恢复删除的表。★ UNDROP 就是 Time Travel 的一个应用——DROP 掉的对象没真消失，只是在保留期里被标记为已删除，所以 只有「有 Time Travel 的对象」才能 UNDROP：DATABASE / SCHEMA / TABLE。先问「这东西有没有 TT」，就不用背 UNDROP 的适用清单
  • Standard 版：0 或 1 天；Enterprise+ 永久表：最多 90 天
  • DATA_RETENTION_TIME_IN_DAYS 控制，四个层级都能设：Account → Database → Schema → Table，最细到 Table。下层继承上层、可覆盖；在 DB/Schema 上设值会作用于其下所有已有和新建对象（除非对象自己显式设过）
  • 设为 0 = 关闭 Time Travel：不能 UNDROP、不能 AT/BEFORE。但永久表仍有 7 天 Fail-safe（只能找 Snowflake 支持，自己碰不到）
  • CREATE OR REPLACE 本质是 DROP + CREATE，不是"覆盖内容"。旧对象进了 Time Travel，理论上能 UNDROP——但新对象已经占用同名，直接 UNDROP 会因命名冲突报错，得先把新对象改名腾位置，再 UNDROP 旧的
  • Fail-safe：Time Travel 结束后额外 7 天，仅永久表，只能由 Snowflake 支持人员恢复，用户无法查询，且照常收存储费

★ 三个数字先分「性质」再记值：默认 1 天（TT，所有版本）· 固定 7 天（Fail-safe，不可改）· 上限 90 天（TT，Enterprise+，要手动设）。

数字属于谁性质
1 天Time Travel默认值（问 default 只能是它）
7 天Fail-safe固定，不可配
90 天Time Travel最大值，需 Enterprise+ 且手动设

⚠️ 7 天是本题唯一的诱饵，因为它两处都出现：既是 Fail-safe 的固定长度，又是 Enterprise 常见的 TT 配置值——但它从来不是任何东西的默认值。看到 default 这个词，先问「默认/固定/上限，问的是哪一个」，再报数。

★ 克隆的权限规则（反直觉，高频）：口诀「克隆有里无外 —— 里面的对象和权限都带走，外壳自己的权限归零」。

克隆一个 database，什么跟着走？
库自身的权限（谁能访问这个库）❌ 不克隆——只有执行克隆的 role 拥有它
库内部 schema / table 上的权限✅ 克隆
Future grants（GRANT … ON FUTURE）❌ 不克隆——克隆是时间点快照，只复制当时已存在的东西

设计动机（记住它就不用背规则）：克隆常用来造 dev/test 环境。库内部的权限结构要原样保留（省得重新授权），但这个新库该给谁看必须由你重新决定——否则一克隆，所有能访问生产库的人自动就能访问测试库，等于权限泄漏。

★ 口诀：写死库名的，克隆后还认老家；不写库名的，跟着新家走。

克隆复制的是对象定义的文本，不会去改写里面的引用。所以克隆出来的 view / 存储过程 / task 里，只要引用是 fully qualified（prod_db.public.orders 三段写全），它照样指向原库；只有非限定或 schema 级引用（public.orders）才会在新库里自洽。

克隆出的 view/proc 里写的是克隆后指向
prod_db.public.orders（完全限定）原库 prod_db ⚠️
public.orders / orders（非限定）克隆后的新库 ✅

真实踩坑：克隆生产库到 dev_db 做测试，结果 dev_db 里的存储过程往生产表写数据。防范做法就是在 view/proc 里尽量不写库名，让克隆能自洽。

⚠️ 题眼是 fully qualified 这个词本身——它一出现，问的就不是「克隆带不带走对象」，而是「引用还指着谁」。看到它先想「文本没被改写」。

顺序：Active → Time Travel（0–90天）→ Fail-safe（7天）→ 彻底删除

★ 删除 ≠ 停止计费。存储费一直收到 Fail-safe 也过期 为止。

Active ──DELETE/DROP──▶ Time Travel(0–90天) ──▶ Fail-safe(7天) ──▶ 彻底清除
  计费                      仍计费                  仍计费          停止计费 ✅

原因是微分区不可变(immutable)：DELETE 一行不会去改原分区，而是写一个新分区、把旧分区标记为历史版本。旧分区还实实在在躺在存储里、随时可被 Time Travel 召回——东西还在，钱就还收。

所以「删了表为什么存储没降」的答案永远是这条；要查各段各占多少，用 TABLE_STORAGE_METRICS。永久表最坏情况 = TT 90 天 + FS 7 天 = 97 天后才停止计费。

★ 题眼 “both querying and restoring” → 只有 Time Travel 两样都能干。

口诀：Time Travel 能看能救，Fail-safe 只能救、还得求人。

Time TravelFail-safe
时长0–1 天（Standard）/ 0–90 天（Enterprise+）固定 7 天，紧接 TT 之后
谁能用用户自己，SQL 直接操作只有 Snowflake 支持团队，要开工单
能查询吗✅ AT / BEFORE❌

⚠️ 「用于 querying 的功能」＝ 能执行查询这个动作，不是「能让查询变快」。Clustering key / SOS / QAS / MV 都是优化手段，选项问「哪个功能用来查询历史数据」时它们全部出局。Cloning 也不算「查询历史」——它产出的是一个新对象。

Domain 5：数据协作（10%）

Secure Data Sharing 基本原理

  • 共享的是元数据引用，不复制数据，消费者查询时用自己的 warehouse 算力，提供者不承担计算成本
  • 提供者只付存储费；消费者只付计算费
  • 数据实时：提供者更新，消费者立刻看到
  • 共享对象只能是：表、外部表、安全视图、安全物化视图、安全 UDF
  • 消费者对共享数据只读，且不能再共享（no reshare，默认）
  • 不能放进 share 的：普通 View（必须 Secure View）、普通物化视图、Stored Procedure、Stage / Pipe / Task、Sequence。记：共享的东西必须是 Secure 的——普通 view 会暴露底层定义
  • 消费方要 CREATE DATABASE … FROM SHARE provider.share_name 才能用；该库只读，不能建表、不能 DML
  • Share 是容器不是查询：CREATE SHARE 先建一个空壳，再用 GRANT … TO SHARE 逐个塞对象进去。不存在 CREATE SHARE AS SELECT ... 这种写法——那是把 View 的语法搬过来的造词陷阱

★ Revoke 权限 = 掐断指针，consumer 端瞬间归零，没有任何"降级但可用"的中间态。因为从头到尾都没复制过数据——consumer 一直靠的是指向 provider 存储的元数据引用，revoke 就是掐断这条引用，不存在"留一份快照/副本"这种缓冲机制，更不会让 consumer 突然开始承担存储费（它本来就没存过东西）。

⚠️ 别用其他云厂商"断开同步后保留最后一份快照"的经验类比——Snowflake 的哲学是干脆、不留驻留：GRANT 时不复制，REVOKE 时也没什么可"回收"的，直接变不可访问。

★ 可分享对象只有五种：Table、External Table、Secure View、Secure Materialized View、Secure UDF——"Secure" 前缀不是可有可无的修饰词，是硬性前提。

对象要不要 Secure 前缀
Table / External Table不需要，本身即可分享
View✅ 必须是 Secure View，普通 view 不能分享（会暴露底层定义）
Materialized View✅ 必须是 Secure Materialized View，普通物化视图不能分享
UDF✅ 必须是 Secure UDF，普通 UDF 不能分享

⚠️ 完全不能分享（不存在 secure 版本可救）：Stored Procedure、Stage / Pipe / Task、Sequence、Stream。看到题干把 View/Materialized View/UDF 直接写成不带 Secure 的形式，先怀疑它是陷阱，别只看对象类型对不对。

⚠️ Files 干扰更隐蔽：它压根不是数据库对象（不是 table/view/UDF 这类可被 GRANT 的东西），Secure Share 分享的是数据库对象，Files 从一开始就不在候选范围里，不需要靠"是不是 secure 版本"去排除它。

问的是答案

共享必 Secure，零拷贝，算力自付。

⚠️ 另一条免费判据：读不通的句子通常就是错的。例如 loaded into a cloud provider as a consumer account——cloud provider 是 AWS/Azure/GCP，consumer account 是 Snowflake 账户，两个层级被搅在一起。选项语法混乱 = 出题人在硬凑错误项，不必细究含义。

★ Secure View/UDF 跨库引用时，普通 SELECT 权限不够，还得单独授 REFERENCE_USAGE——这是 Snowflake 专门为"view 属于 A 库，但查询引用了 B 库对象"设计的权限。

同库场景：share 上只需 SELECT（view 本身 + 底层表）即可，标准流程。
跨库场景：view 定义里 JOIN/引用了另一个数据库的对象 → 必须在被引用的那个库上对 share 额外授予 REFERENCE_USAGE ON DATABASE，否则那层跨库引用不合法生效——Share 的设计原则是"少暴露"，不会因为 view 能 SELECT 就自动放行它牵连到的其他库。

⚠️ 题干出现"secure view 引用了另一个数据库的表/对象"这类描述 → 别停在 SELECT，先想到 REFERENCE_USAGE。

⚠️ 「类型」问的是发布物，不是参与方。Provider / Consumer 是角色，不是 listing 类型——题干问 types of listings 时它们全是干扰项。

⚠️ 官方术语是 Provider，从来不叫 Vendor。选项里出现非官方词汇 → 先怀疑。（同 key partitions、Hive connector）

Listing 的跨区域行为（偏难，考纲 5.3）

★ 核心区分：listing（挂牌）≠ data（数据）。
Listing = 橱窗展示页（标题、描述、样例、价格）——是元数据，很轻，会自动复制到你选中的所有 region。
Data = 数据本体——躺在你自己的 region 里，不会自动跟过去；要让别的 region 真正读到，必须做跨区复制（replication），费钱费时间。

口诀：橱窗自动飞，数据得付费搬 —— 有人要了再搬。

推论（官方推荐做法）：standard listing 可以等第一个消费者来要时再复制数据过去——跨区复制贵，没客户的 region 不必提前烧钱。（对比：paid listing 要立刻交付，通常得预先备好。）

⚠️ 两条「范围放得太宽」的错误说法：
①「没有 Snowflake 账户的人也能直接消费」= False——消费者必须在某个 region 有 Snowflake 账户；没有的话只能走 Reader Account（由 provider 代建）。而且 share 是授予账户的，不是给每个 user 建一个 share。
②「同一 organization 下的任意账户自动可访问」= False——share 必须显式授予特定账户。这和克隆那题同源：Snowflake 一贯是显式授权，什么都不自动继承。

⚠️ ORGADMIN 在这里是「正确知识点、错误场景」：它确实用于账户复制 / failover，但发布 listing 到远程 region 走的是 listing 机制，不需要手动 link accounts。

  • 跨区域/跨云共享：底层需要数据库复制（replication）把数据复制过去，或用 listing 的自动复制。Data Exchange 不能绕过这条限制——它只是私有目录/门户（管"给谁看"），不改变"share 要求同云同区"的底层物理限制
  • Reader Account：给没有 Snowflake 账户的消费者用。由提供者创建、拥有并付全部计算费用。Reader account 只能读，不能自己加载数据。用 CREATE MANAGED ACCOUNT 创建，SHOW MANAGED ACCOUNTS 查看（Reader Account 官方术语就是 Managed Account）；因为费用记在提供者账上，提供者通常要配 Resource Monitor 防止对方乱跑查询烧钱

★ 共享的计费归属：地主付房租，租客付电费。

项目谁付
存储费（共享数据本体）Provider
计算费（Consumer 查询）Consumer（用自己账户里的 warehouse）
计算费（Reader Account 查询）Provider ← 唯一例外
跨区域复制的数据传输费Provider

⚠️ Egress（出口）费是云厂商（AWS/Azure/GCP）对跨 region / 跨云传输收的网络费，Snowflake 只是转嫁，不是自己定价。触发条件只看一句话：数据有没有跨越 region 或云边界被物理搬运。within a specific region / 同区域内共享 → 不触发 egress；跨区域、跨云的 replication → 触发。题干出现"within a specific region"这类限定词时，它是排除 egress 的关键信息，不是触发条件——别被"data sharing = 跨账户传数据"的直觉带偏。

这不是规定，是架构的必然：存储与计算分离。数据躺在 Provider 的存储里，查询却是 Consumer 在自己账户里启动的 warehouse 跑的——两笔账天然记在两个账户上，不存在「跨账户代付」这种机制。

⚠️ the provider pays for compute 只有在题干出现 Reader Account / managed account 时才对。题干没提 Reader Account 就一律是 Consumer 付。Reader 是白吃白住的客人，房东全包——所以房东要配 Resource Monitor。

★ Reader Account 的「只读」限制的是写，不限制读出去。

口诀：Reader 只读不写，但读得出去 —— 能查、能建仓、能导出；不能改、不能传、不能再分享。

能 ✅不能 ❌
查询共享数据（SELECT）DDL / DML（建表、改数据）
创建 virtual warehouse 跑查询上传自己的数据进 Snowflake
Web UI 下载结果、COPY INTO 外部 stage 卸载数据再分享给别人（no re-share）
JDBC / ODBC / Python connector 拉数据Time Travel、Cloning

★ 商业含义（考点）：Data Sharing 在技术上无法防止数据外泄——看得到的部分一定拿得走。控制手段只有两条：合同/法律，或用 Secure View / Row Access Policy 限制他看得到的范围。

复制与故障转移

  • Replication：把数据库/账户对象复制到其他账户或区域
  • Failover / Failback：需要 Business Critical 及以上
  • Replication group / Failover group：一致性地复制一组对象

★ Replication 是空间维度（这个区域整个挂了怎么办），Time Travel / Fail-safe 是时间维度（我误删了一张表怎么办）——"多一份数据"不代表解决同一个故障场景，题干问的是哪种灾难要先分清。

Database Replication 本身 Standard 起即可用（只读副本，可做读扩展/跨区分发）；Failover/Failback（Business Continuity）才要 Business Critical+。选项把 replication 和 failover 捆在一起时，按门槛最高的算（与前面「捆绑功能按门槛最高算」规则同源）。

⚠️ secondary database 在 failover 真正发生之前只能读，不能写。题干问"能不能对 replica 做 DML" → 答案是不能。

⚠️ 不会被复制过去的东西：Time Travel 历史、Fail-safe、临时表/瞬态表的内容不跨区域带走；副本上的 Time Travel 是重新开始计算的，不是把主账户的历史搬过去。复制的是"当前数据 + 对象定义"，不是"连带历史一起搬家"。

1. Snowpark

  • 是什么：在 Snowflake 内部用 Python / Java / Scala 写数据处理逻辑的 DataFrame API。代码下推（push-down）成 SQL 在 Snowflake 引擎里跑，数据不出仓。
  • 对比：Spark connector 是把数据搬出去算；Snowpark 是把计算搬进来。这是最常考的一句。
  • Snowpark-optimized warehouse：内存/CPU 加强型，用于大内存 UDF、ML 训练。普通 warehouse 也能跑 Snowpark，只有内存吃紧才需要换。
  • UDF / UDTF / Stored Procedure 都可以用 Python 写。Python 包来自内置的 Anaconda channel（无需自己装）。
  • Snowpark Container Services：跑容器化的长驻服务（需要 compute pool，不是 warehouse）。考点很浅，知道"跑容器、用 compute pool"即可。

2. Snowflake Notebooks

  • Snowsight 里的原生 notebook，cell 支持 SQL / Python / Markdown 混写，结果可直接互相引用。
  • 运行在 warehouse（或 container runtime）上，可加入 Git 仓库做版本管理，可被 Task 调度。
  • 权限走标准 RBAC，notebook 是 schema 级对象。

3. Streamlit in Snowflake (SiS)

  • 用 Python 直接在 Snowflake 里建数据应用 UI，无需外部 web 服务器。
  • 应用在 owner's rights 或 caller's rights 下运行——考点：默认 owner's rights，意味着查看者看到的数据由应用所有者的权限决定。
  • 可通过 Native App 分发给其他账户。

4. Snowflake Cortex（AI/ML）★ 最可能出现的新考点

分类 内容
Cortex LLM Functions SQL 里直接调大模型：COMPLETE（通用生成）、SUMMARIZE、TRANSLATE、SENTIMENT、EXTRACT_ANSWER、CLASSIFY_TEXT、EMBED_TEXT_*
Cortex Analyst 自然语言 → SQL。依赖 semantic model（YAML 语义模型文件），不是直接问原始表
Cortex Search 托管的混合检索服务（向量 + 关键词），是做 RAG 的检索层。注意与 Search Optimization Service 完全不同——后者是加速 SQL 点查的，前者是文本语义检索
Document AI 从 PDF/图片等非结构化文档里抽取字段，可微调
  • 计费：serverless，按 token 计费，不占用你的 warehouse（但 SQL 本身要 warehouse 执行）。
  • 数据不出 Snowflake 边界——这是官方最强调的卖点，几乎必考。
  • 权限：使用 LLM 函数需要 SNOWFLAKE.CORTEX_USER database role（默认授予 PUBLIC，可回收）。
  • 区域可用性有限，不可用区域需开启 cross-region inference 参数。

必须区分的三对： Cortex Search（语义检索）vs Search Optimization（SQL 点查加速） Cortex Analyst（NL→SQL，要语义模型）vs Cortex COMPLETE（通用 LLM 调用） Snowflake ML（建模）vs Cortex（调现成模型）

5. Snowflake ML

  • ML Functions（无需写模型）：FORECAST（时序预测）、ANOMALY_DETECTION、CONTRIBUTION_EXPLORER（归因分析）、CLASSIFICATION。都是 SQL 调用、serverless。
  • Model Registry：在 Snowflake 里存模型版本、元数据，可直接 SQL 推理。
  • Feature Store：特征的集中定义与复用。
  • 考点极浅：知道"这些是 SQL 就能调的托管 ML，不用搬数据"。

6. Dynamic Tables ★

  • 声明式：你只写 CREATE DYNAMIC TABLE ... TARGET_LAG = '5 minutes' WAREHOUSE = wh AS SELECT ...，Snowflake 自动增量刷新。
  • 替代 Stream + Task 手写管道。考点：题目描述"想要低维护的增量 ELT" → Dynamic Table。
  • TARGET_LAG 是"数据最多落后多久"的目标，不是刷新间隔。也可设 DOWNSTREAM（由下游需求决定）。
  • 刷新模式：Incremental（增量，首选）或 Full（查询含不支持增量的构造时自动降级，成本高）。
  • 计算：刷新用你在 WAREHOUSE = 里指定的 warehouse（也可选 serverless 模式，由 Snowflake 管资源）。关键不在用哪种算力，而在"刷新由 Snowflake 触发，不由你调度"。
  • 与物化视图的区别：MV 只能单表、不支持 JOIN；Dynamic Table 支持 JOIN、聚合、多表、链式。

★ Dynamic Table vs Stream + Task —— 最该记的一条：产出物的「所有权」不同。

Dynamic TableStream + Task
你写什么目标状态（一句 SELECT + TARGET_LAG）过程（MERGE/INSERT 逻辑 + CRON 调度）
产出物Dynamic Table 本身，由定义查询决定内容普通表
能不能改（DML）不能。INSERT / UPDATE / DELETE 全部不允许，你只能查能，随时 DML，它就是张普通表
谁触发刷新Snowflake（按 TARGET_LAG 自己决定何时刷）你（Task 的 schedule）
控制力低（换来零维护）高（换来你自己维护）

为什么不能 DML：Dynamic Table 的内容完全由定义查询推导，Snowflake 要保证它随时都等于"那句 SELECT 现在的结果"。你手动改一行，下次刷新就会被覆盖掉——所以干脆禁止。
一句话：Stream + Task 是"你告诉它怎么做"，Dynamic Table 是"你告诉它要什么"。

选择题提示词（看到就能定选项）：

题干出现选
with minimal maintenance / declarative / simplest pipelineDynamic Table
freshness requirement expressed as lag（用"落后多久"表达新鲜度）Dynamic Table（TARGET_LAG）
custom procedural logic / call stored procedure / conditional branchingStream + Task
需要对结果表手工修正 / 补录 / 打补丁（DML）Stream + Task

后两行是同一个道理的两面：凡是题干要求你"能插手"——不管是插手过程（存储过程、条件分支）还是插手结果（DML 改数据）——都只能是 Stream + Task。Dynamic Table 的全部卖点就是不许你插手，换来零维护。

7. Apache Iceberg Tables ★

  • 开放表格式，数据和元数据存在你自己的云存储桶（external volume），不在 Snowflake 内部存储。
  • 两种目录（catalog）模式，必考：
  • Snowflake 作为 catalog：可读可写，性能接近原生表，支持 Time Travel、克隆等大部分特性
  • 外部 catalog（AWS Glue / 外部 Iceberg REST / 对象存储文件）：只读
  • 需要先建 EXTERNAL VOLUME 对象。
  • 没有 Fail-safe。存储费付给云厂商，不付给 Snowflake。
  • Catalog Linked Database：自动同步外部 catalog 里的表。
  • 用途题眼："想让 Spark/其他引擎也能直接读同一份数据" → Iceberg。

8. Snowpipe Streaming

  • 行级直接写入，不需要先落文件到 stage，延迟秒级。

9. Trust Center

  • Snowsight 里的安全态势管理面板，按 scanner package 定期扫描账户配置，给出风险发现与整改建议。
  • 内置包：Security Essentials（免费）、CIS Benchmarks、Threat Intelligence。
  • 需要 TRUST_CENTER_ADMIN / TRUST_CENTER_VIEWER application role。
  • 题眼："想自动发现没开 MFA 的用户 / 过宽的网络策略" → Trust Center，不是 Access History。

10. Data Classification / Sensitive Data

  • 自动扫描列内容，打上 system tag：SEMANTIC_CATEGORY（如 NAME、EMAIL）+ PRIVACY_CATEGORY（IDENTIFIER / QUASI-IDENTIFIER / SENSITIVE）。
  • 流程：SYSTEM$CLASSIFY 或自动分类（auto-classification，需 schema 级开启）→ 打 tag → 可接 tag-based masking policy 自动脱敏。
  • 区分题：Object Tagging = 你手动打标签；Data Classification = Snowflake 自动识别并打标签。官方样题考过。

★ 支持的列类型只有三大类结构化类型：数值（NUMBER/DECIMAL/INT/FLOAT/DOUBLE）· 字符串（VARCHAR/CHAR/STRING/TEXT）· 日期时间（DATE/TIME/TIMESTAMP_*）。

判据：分类靠逐值看内容像不像 PII，所以列必须是「一列一个标量值」。→ VARIANT / OBJECT / ARRAY（半结构化）和 GEOGRAPHY / BINARY 都不支持——里面是嵌套结构或二进制，没有可比对的标量模式。另一个方向：能被 Masking Policy 遮的类型，基本就是能被分类的类型。

⚠️ 别因为「FLOAT 里不会有邮箱」就排除数值。数值列照样承载 PII：AGE、SALARY、纯数字的 PHONE_NUMBER、邮编、纬经度——它们多半被判为 QUASI_IDENTIFIER。问「支持哪些类型」是问技术能力，不是问「哪种最可能命中」。

11. Git Integration

  • Snowflake 可直接连 GitHub/GitLab 等仓库，把仓库作为一个 Git repository stage 挂进来。
  • 需要 API INTEGRATION（指向 git 域）+ 可选 SECRET 对象存凭证。
  • 用途：把 SQL 脚本、Streamlit 应用、Notebook 版本化，配合 EXECUTE IMMEDIATE FROM @repo/... 做 CI/CD。

A0. 会把句子读反的短语 —— 最贵的一类错

这类错和知识无关：你知道答案，但把题干读反了，于是笃定地选错。比不会做更亏，因为不会做至少会犹豫。
处理方式：看到下列短语，先在脑子里把整句翻成中文再判断，不要凭语感。

英文正确含义
in lieu of而不是（= instead of）
as opposed to而不是（对比前者）
other than除……之外（排除）
rather than而不是
short of除非做到 / 达不到
barring / absent除非有 / 在没有……的情况下
notwithstanding尽管（= despite）

范例（真题级）：“Snowflake's data warehouse is built from the ground up for the cloud, in lieu of being based on an existing database or platform such as Hadoop.”

A. 限定词（Qualifiers）—— 看到就圈出来

同一道题的四个选项可能都是正确做法，限定词决定选哪个。这是 SnowPro 最主要的失分点。

英文 含义 它在暗示什么答案
MOST granular / finest 最细粒度（granule = 颗粒）
coarse-grained = 粗粒度
granularity = 「最小算到什么单位」，如 per-second/per-core granularity = 时间算到秒、资源算到核		 选最小的那个层级。如 DATA_RETENTION_TIME_IN_DAYS 四层都能设 → 答 Table，不是 Database。没有这个词时四个选项可能全对，限定词才是唯一筛选条件
MINIMUM edition / version 最低要求 选够用的最低那档，不是功能最全那档。如 Secure Data Sharing → Standard（Enterprise 也有，但不是最低）。
⚠️ 反过来：available with Enterprise 问的是「用得上吗」，Standard 的功能也算对（版本向上累积）；只有 only in / requires / minimum 才是问起步档
PRIMARY / MAIN purpose 主要用途 核心功能，不是附带效果
FIRST step 第一步 顺序题，注意先后而非对错
NOT / EXCEPT 反选 找错的那个——三个对一个错，别顺手选第一个正确的
dedicated 专用的、专门指派的 诱导你只否定「专用」这一层。如「Snowpipe 需要 dedicated warehouse？」→ 不是「共享一个就行」，而是压根不需要 warehouse。看到 dedicated，先问「这东西根本需不需要」
名词中心词：execution plan / physical storage / metadata about 不是限定词，是词组的重心 重心在最后那个名词上，不在你先认出来的那个词上。execution plan → 出计划 = Cloud Services（不是 execution → Compute）；physical storage → Storage；metadata about X → Cloud Services。看到 execution 别急着选 Compute，先看它后面还有没有词
MOST cost-effective 最省钱 倾向 serverless / 更小 warehouse / transient 表 / 结果缓存
MOST efficient / performant 最快 倾向 clustering / SOS / QAS / 加大 warehouse；加载场景倾向 Snowpipe auto-ingest（事件驱动）而非 Task + COPY（轮询）。「能用」的选项技术上没错，但比较级要的是「最」
BEST practice 官方推荐做法 不是"能跑通"，是文档里写的那个（如自定义角色挂 SYSADMIN）
LEAST amount of effort / operational overhead 最省人力 强烈倾向托管/声明式方案：Dynamic Table > Stream+Task；Snowpipe > 手写 COPY 调度
without additional cost 不额外花钱 结果缓存、元数据缓存、克隆、MFA、Time Travel（保留期内）
without any additional configuration 开箱即用 排除需要建 integration / policy / external volume 的选项。凡是要「选版本」的功能，基本都要配置（脱敏、行访问、Tri-Secret…）
automatically 自动 排除需要人工触发的选项（如手动 REFRESH）
near real-time / lowest latency 最低延迟 Snowpipe Streaming（秒级）> Snowpipe（~1 min）> Task 调度
minimal impact on running queries 不影响在跑的查询 改 warehouse 大小只对新查询生效；Suspend（非 Immediate）让查询跑完
must / requires / required 硬性要求 找唯一必要条件，不是"推荐"。反向陷阱：把一条 best practice 写成 requires → False（例：「加载要求文件 ≤ 16 MB」= False，源文件不限大小，100–250 MB 只是建议）
ALWAYS / NEVER 绝对表述 选项里出现绝对词，通常是错的（但题干里的要认真对待）。
both / all 是最爱用的一个字：「internal 和 external stage 都计存储费」= False（只有 internal）。看到 both，把两边分开各判一次。
已知例外（背下来）：「所有微分区的所有列都自动收集元数据」= True；「数据始终加密（静态+传输）」= True；「Federated/SSO 在所有版本都支持」= True。
判据：属于「架构根基」或「基础安全」的绝对表述是真的；涉及功能档次、配置、上限的才是陷阱
MAY / CAN / AT TIMES / SOMETIMES / IN SOME CASES 软化措辞（绝对词的反面） 只要存在一种情况成立，整句就是 True——不用去证明「每次都这样」。
例：「大仓库有时可能启动更慢」= True（通常有预热池，秒级；但资源紧张时会慢）。
口诀：看到 may/at times 找一个成立的例子；看到 always/never 才去找反例。

Select all that apply / Which TWO / Which THREE → 题目会明说选几个。选够数量才计分，少选不给分。 第一遍做题时先把数字圈出来。
